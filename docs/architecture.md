# Architecture (MRI-001)

Data flow: provider adapter -> immutable raw snapshot and metadata -> parse into canonical daily schema -> calendar/price/adjustment validation -> content-addressed Parquet plus manifest -> causal features and separate forward targets -> fold-specific models -> forecasts -> aligned scores -> report. MRI-004 ends at deterministic feature and target tables.

`mri.data` owns provider I/O, parsing, validation, calendar checks and persistence. Provider adapters return source bytes plus request metadata; downstream code receives canonical typed frames, never provider-specific columns. `mri.features` owns deterministic, unit-tested transforms and keeps forward labels separate from features; it does not certify point-in-time source availability. `mri.models` will fit/filter state estimators and baseline volatility models; `mri.forecasting` will map information at an origin to horizon-specific variance and event probabilities; `mri.evaluation` will own split/purge, metrics and dependence-aware uncertainty; `mri.experiments` will record frozen configs, seeds, artifacts and attempted variants; `mri.reporting` will render auditable reports. No model implementation exists yet.

Planned interfaces: a model `fit(train_features, train_targets, config, seed)` returns fitted state and diagnostics; `predict_as_of(origin_features, horizon)` returns positive daily variance and/or calibrated event probability plus provenance. A regime model must expose `filter_as_of` based on observations no later than the origin. Splitters supply explicit train and prediction session indices, label maturity cutoff and purge audit. These are design contracts, not implemented APIs.

Data fetch is an explicit command. Offline loading uses saved snapshots; no import triggers network I/O. Snapshot names and manifests are content-addressed, and writes are exclusive. Dataset files, snapshots and reports are ignored by Git.
